# ADR-001: Монолит как текущая система (As-Is)

- Status: Accepted
- Date: 2026-09-19
- Deciders: команда разработки CinemaAbyss

## Context

Нужно зафиксировать текущую систему до проектирования To-Be. Задание 1 требует понять As-Is и домены, а не описывать будущие микросервисы. В репозитории один процесс Go (`src/monolith/main.go`) и одна PostgreSQL (`src/database/init.sql`). Клиенты (web, mobile, TV) обращаются к одному REST API; BFF нет.

На схеме As-Is не смешиваем задел To-Be из compose: `movies-service`, `proxy`, Kafka, events — это следующий шаг, не текущий монолит.

В кейсе описаны возможности, которых в коде нет: аутентификация, избранное, оценки как API, скидки, вызов рекомендательной системы, внешние лояльность / маркетплейсы / платёжные шлюзы. Таблицы `views` и `user_ratings` есть в SQL, HTTP-хендлеров для них нет.

## Decision

As-Is документируем как:

- **один процесс** — монолит на Go, порт `:8080`;
- **одна БД** — PostgreSQL, все домены в одной схеме;
- **синхронный REST → SQL** — каждый HTTP-запрос обрабатывается в том же процессе и сразу читает/пишет в Postgres.

Публичные маршруты:

| Маршрут | Методы | Назначение |
| --- | --- | --- |
| `/health` | GET | Проверка живости |
| `/api/users` | GET (список / `?id=`), POST | Пользователи |
| `/api/movies` | GET (список / `?id=`), POST | Фильмы (+ жанры в `movie_genres`) |
| `/api/payments` | GET (список / `?id=` / `?user_id=`), POST | Платежи |
| `/api/subscriptions` | GET (список / `?id=` / `?user_id=`), POST | Подписки |

Домены **users**, **movies**, **payments**, **subscriptions** пока **логические** — в коде нет модульных границ, общий `main.go` и один пул соединений к БД.

## Alternatives considered

- **Сразу рисовать To-Be на Context** — схема перестанет описывать то, что есть; виден proxy, Kafka и отдельный movies-service там, где сейчас один процесс.
- **Три отдельных ADR** (монолит / sync REST / Postgres) — избыточно на этапе As-Is; одно решение покрывает весь текущий контур. Разделим, когда перейдём к To-Be.
- **Модульный монолит с отдельными пакетами** — в репозитории нет пакетной структуры по доменам, это уже другой контур.

## Consequences

- **Positive:** одна схема C4 Context и один ADR совпадают с кодом; границы доменов можно наметить без преждевременного split.
- **Negative:** все домены в одном процессе и одной БД — риск связанности и «большого комка»; отсутствие auth и части таблиц в API создаёт разрыв между кейсом и реализацией.
- **Follow-up:** задание 1 (продолжение) — C4 Container To-Be, нарезка доменов; триггер на вынос сервиса — отдельный цикл деплоя или отдельная команда.
